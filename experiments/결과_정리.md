## 1. 검색 필터: SelfQuery → 메타데이터 직접 필터

- **기준선의 문제**: 분석 검색마다 LLM(query constructor)이 질문 문장을 Chroma 필터로 다시 만들었다. 느리고, 필터를
  틀리면 조건과 다른 상품이 나오거나 결과가 0개가 됐다.
- **해결**: 앞 단계에서 이미 추출한 조건(판매처·모델·지면·가격)을 메타데이터 필터에 그대로 넣는다(LLM 호출 제거).
- **지표를 고른 이유**: LLM 호출 제거 효과는 지연(p50/p95)으로, 빨라지면서 정확도가 떨어지지 않았는지는 정밀도·결과 0개
  비율·질문 단위 성공으로, 이전 방식이 왜 실패했는지는 필터 구조를 파싱한 원인 분류로 본다.
- **결과** (30문항 × 3회 × 2방식 = 180회, 커밋 46c791c)

| 지표 | SelfQuery | 직접 필터 |
|---|---|---|
| 검색 지연 p50 / p95 | 1,364ms (CI 1,314~1,403) / 1,874ms | **233ms** (CI 228~241) / 330ms |
| 정밀도(반환 문서 중 조건 모두 만족) | 85.4% (187/219) | 100% (261/261) |
| 결과 0개 실행 | 17/90 | 0/90 |
| 질문 단위 성공(3회 다수결) | 17/30 | 30/30 (짝 비교 13 : 0, p=0.0002) |

  - SelfQuery 지연의 84.8%가 LLM 단계. (예전 노트북의 51.4%는 n=3에 LLM을 두 번 호출해 잰 값이라 대체한다.)
  - SelfQuery 실패 39회의 원인(중복 가능): 가격 범위 오해 15("20만원대" → "= 200,000원"), 질문에 없는 조건을
    지어냄 11("퓨처"를 상품 분류 필터에), 판매처 누락 10, 지면 누락 9, 판매처를 엉뚱한 필드에 8, 모델명 오배치 3,
    경계값 차이 10("이하" → "미만", 경미).
- **한계**: 직접 필터 쪽은 정답 조건을 입력으로 받았으므로 정밀도 100%는 거의 구성상 결과다(조건 추출 정확도는 실험 4).
  질문은 실제 DB 조합에서 규칙으로 생성한 30개, 사람 검수 없음. 측정 범위는 검색 단계만.

## 2. LLM 채점 단계(CRAG·Self-RAG) ablation — 효과 없음을 확인

- **기준선의 문제**: hallucination을 막으려고 생성 전 문서 관련성 채점(CRAG)과 생성 후 근거 검증(Self-RAG)을 넣었지만,
  실제로 효과가 있는지 측정한 적이 없었다.
- **방법**: 같은 코드에서 두 채점 단계만 통과 처리(=도입 전)한 쪽과 비교. 실시간 크롤링은 막고 로컬 DB만 사용.
- **지표를 고른 이유**: 채점 단계의 목적이 "근거 없는 주장 감소"이므로 생성 모델과 다른 판정 모델(gpt-4o)로 답변당
  근거 없는 주장 수를 세고, 가격·링크는 코드로 결정적으로 대조했다. 부작용은 지연·LLM 호출 수·정답 있는데 "결과 없음"으로 본다.
- **결과** (30문항 × 2회 × 2 = 120회, 커밋 46c791c)

| 지표 | 채점 끔 | 채점 켬(당시 서비스) |
|---|---|---|
| 답변당 근거 없는 주장(gpt-4o 판정) | 2.63개 (CI 2.27~3.02) | 2.43개 (CI 2.07~2.80) |
| 질문 단위 짝 비교 | — | 켬이 적음 8, 끔이 적음 7, 동률 12 → **p=1.0** |
| 지연 p50 | 4,332ms | 5,495ms (+27%) |
| 실행당 LLM 호출 | 1.00회 | 3.02회 |
| 정답 있는데 "결과 없음" | 0/60 | 6/60 |

  - CRAG가 뺀 문서 99건 중 91건이 조건을 만족하는 정상 문서(과잉 제거) → Q03·Q14·Q20을 "결과 없음"으로 만듦.
  - Self-RAG는 외부 판정이 근거 없다고 본 답변 52건을 52건 모두 통과시킴.
  - 근거 없는 주장의 대부분은 "경량"(45회)·"편안한 착용감"(25회)·"접지력 우수"(18회) 같은 기능 설명 →
    생성 프롬프트의 "주요 특징: 기능 키워드 2개↑" 규칙이 문서에 없는 정보를 요구한 것이 원인.

## 2-b. 원인 수정 + 결정적 검사 → 서비스 반영

- **해결**: 생성 프롬프트의 그 한 줄을 "문서에 있는 지면·연령대만"으로 교체(프롬프트를 YAML로 분리해 버전 관리),
  CRAG 자리는 비축구화 상품명 제외 규칙, Self-RAG 자리는 답변 가격·URL을 코드로 대조하는 검사로 바꿈.
- **결과** (30문항 × 2회 × 3방식 = 180회, 같은 세션, 커밋 46c791c + 실험 코드로 교체)

| 지표 | A 당시 서비스 | B 프롬프트만 수정 | C 수정 + 결정적 검사 |
|---|---|---|---|
| 답변당 근거 없는 주장 | 2.56개 | 0.47개 | **0.23개** (CI 0.10~0.40) |
| 근거 없는 주장 1개 이상인 답변 | 96.3% | 18.3% | 15.0% |
| 지연 p50 | 5,581ms | 4,365ms | **4,122ms** |
| 실행당 LLM 호출 | 3.02회 | 1.00회 | 1.00회 |
| 정답 있는데 "결과 없음" | 6/60 | 0/60 | 0/60 |
| 축구공이 답변에 노출 | 0 | 2회 | 0 |

  - 질문 단위 짝 비교: C가 A보다 적음 25, A가 적음 0 (p<0.0001).
- **서비스 반영 후 검증** (실제 서비스 함수 호출, 30문항 × 2회, 커밋 720817d 코드):
  근거 없는 주장 0.28개/답변(CI 0.13~0.47), 결과 없음 0/60, 정답 있는데 상품을 못 보여줌 0/60, 지어낸 가격·링크 0/170·0/340,
  보여준 상품 수 106 → 170개, 지연 p50 5,226ms, LLM 호출 1.02회. 실제 크롤링을 켠 5문항도 오류·근거 없는 주장 0.
- **한계**: 판정자가 LLM이다. 사람 검수 결과 — 실험 2·2-b 표본 20건은 판정과 일치, 최종 검증 표본 10건 중 "근거 없음" 3건은
  모두 판정자 오판(예: 문서의 "59400원"을 "₩59,400"과 다르다고 봄) → 0.28은 **상한**으로 보고한다. 남은 지적의 다수는
  DB 데이터 문제(상품명 '쥬니어'인데 연령대 '성인용', 크롤 단계에서 섞인 이상한 사이즈 숫자). C의 결정적 검사는 채점 규칙과 같아
  링크·문서 단계 지표가 좋아지는 건 구성상 결과(핵심 지표인 근거 없는 주장 수는 별도 모델이 판정). "가격 범위를 숫자로 함께
  전달" 수정은 평가셋 Q11·Q20을 보고 찾았으므로 과적합 가능성이 있다.

## 3. 크롤 캐시 재측정 (사용자 응답 전체 기준)

- **기준선(기존 벤치마크)의 문제**: n=3, 판매처 1곳, 키워드 1개. 크롤 도구 시간만 재서 hit(파일 확인만)의 7.61ms는
  거의 구성상 당연한 숫자였고, hit 결과가 miss와 같은지도 확인하지 않았다.
- **방법**: 쌍마다 비운 임시 캐시로 miss(실제 크롤링) 후 바로 hit. 사용자가 기다리는 분석 응답 전체(크롤+검색+생성)와
  그 안의 크롤 단계 시간, hit·miss 문서 동일 여부를 기록. 실험 후 로컬 DB는 백업으로 복원.
- **결과** (판매처 4 × 시리즈 3 × 2회 = 24쌍, 커밋 90158ef; 크레이지11·레드사커는 오전 사이트 장애로 오후에 재측정)

| 구간 | 캐시 없음(실제 크롤) | 캐시 있음 |
|---|---|---|
| 응답 전체 p50 / p95 | 73,242ms (CI 56,552~84,895) / 179,052ms | **4,948ms** (CI 4,818~5,498) / 6,555ms |
| 크롤 단계 p50 | 67,935ms | 3ms |

  - 쌍별 응답 시간 감소율 중앙값 92.9% (84.3~97.4%). hit와 miss가 같은 문서를 쓴 쌍 24/24.
  - 판매처별 크롤 p50: 카포스토어 35초, 사커붐 65초, 레드사커 69초, 크레이지11 154초.
- **한계**: 실사용 캐시 적중률(로그 필요), 24시간 TTL 동안 가격이 바뀌는 신선도 위험은 측정하지 않음. 외부 사이트 응답은
  시간대에 따라 달라짐(판매처 2곳은 측정 시간대가 다름).

## 3-b. 실패 캐시(negative cache) — 실험 3에서 발견한 문제

- **기준선의 문제**: 판매처 사이트가 다운되면 실패가 캐시되지 않아(맞는 동작) 요청마다 ~23초 타임아웃을 기다린 뒤 기존 DB로
  답했다(응답 ~28초). 또 일부 판매처만 실패한 크롤에서 **실패한 판매처까지 성공 캐시에 24시간 등록**되는 버그가 있었다.
- **해결**: 접속 예외/타임아웃이 난 판매처는 10분간 크롤을 건너뛰고 기존 인덱스로 검색. 실제 성공한 판매처만 성공 캐시에 등록.
- **결과** (장애 주입: 실험 3에서 실제 관측한 타임아웃 24건의 중앙값 23.1초를 주입, 판매처 2곳 × 연속 6요청, 검색·생성은 실제)

| | 첫 요청 | 이후 요청 p50 (n=10) |
|---|---|---|
| 개선 전 | 32.8초 | 28.6초 (CI 28.0~29.8) |
| 개선 후 | 30.2초 | **5.5초** (CI 5.0~6.0) |

- **한계**: 실제 장애가 아닌 장애 주입(주입 시간은 실측값). 실패 기록은 프로세스 메모리 기준이라 워커가 여러 개면 워커마다
  첫 요청은 타임아웃을 겪는다.

## 4. 라우팅: 단일 의도 → 다중 기능 + 조건 게이트

- **기준선의 문제**(git 4306179^): 한 턴에 의도를 하나만 골라 "추천하고 판매처도 알려줘" 같은 요청을 처리할 수 없었고,
  조건이 하나만 있어도 바로 검색했다.
- **해결**(현재): 한 턴에 여러 기능을 받고(requested_capabilities), 상품 탐색은 브랜드·예산·지면을 모두 요구하는 조건 게이트.
- **지표를 고른 이유**: 이번 턴에 부르는 기능 묶음 일치(정답률)를 보되, 현재 정책 기준인 "규칙 준수"(정답이 되묻기)는 구조상
  옛 버전에 불리하므로 정책과 무관한 "의도 파악"(정답에 되묻기 없음)을 따로 본다.
- **질문**: 60문항(분명 14, 다중 12, 애매 22, 도구 없음 12). 프롬프트 예시·기존 테스트 문장과 문자 2-gram 유사도 0.45 미만을
  assert로 확인(초안 중 0.57~0.58이던 2문항은 문장만 바꿈). 애매한 질문 정답은 사전 승인한 규칙.
- **결과** (60문항 × 3회 × 2버전 = 360회 + 수정 후 현재 버전 180회)

| 항목 | 옛 버전 | 현재(수정 전) | 현재(수정 후) |
|---|---|---|---|
| 전체 | 66.7% | 91.7% | **96.7%** (CI 92.9~98.5) |
| 의도 파악 | 75.0% | 88.6% | **95.5%** |
| 규칙 준수 | 43.8% | 100% | 100% |
| 다중 기능 | 0% | 91.7% | 100% |
| 분명한 질문 | 97.6% | 78.6% | 92.9% |
| 지연 p50 | 1,465ms | 1,335ms | 1,284ms |

  - 짝 비교(수정 후 vs 옛): 전체 20 : 2 (p=0.0001), 의도 파악 11 : 2 (p=0.0225), 규칙 준수 9 : 0 (p=0.0039).
  - 수정 전 현재 버전이 분명한 질문에서 진 원인은 LLM이 아니라 규칙 코드: 지면 목록에 HG가 없어 LLM이 잡은 지면을 지웠고,
    시리즈 별칭에 "퓨처" 표기가 없어 상품명을 지웠다(각 3/3 재현) → 수정.
- **한계**: 질문은 직접 작성, 사람 검수 없음. supervisor 단계 제외(실험 5에서 포함). 남은 오답: E07(요청 안 한 판매처 탐색을 붙임,
  LLM 추출 오류), E15("머큐리얼 어때?"를 되묻기로 처리, 정책 해석 영역).

## 5. 단일 ReAct 에이전트(S1) vs 현재 구조(S2)

- **질문**: 라우터 + supervisor + 하위 에이전트 구조가 실제로 필요한가, 단일 에이전트로 충분하지 않은가.
- **설계**: S1 = ReAct 에이전트 1개 + 가짜 도구 4개(상품 탐색·판매처·분석·되묻기). 프롬프트는 S2 의도 분류 프롬프트 원문
  + supervisor 순서 규칙 + 서비스 필수 조건 규칙(S1을 일부러 약하게 만들지 않기 위해). S2 = 실제 조건 추출 → 조건 점검 →
  supervisor(gpt-5.4-nano)를 FINISH/되묻기까지 반복 호출. 다듬기 6문항에서 S1 첫 버전이 18/18이라 조정 0회.
- **결과** (60문항 × 3회 × 2 = 360회 + supervisor 수정 후 S2 180회)

| 항목 | S1 단일 에이전트 | S2 현재 구조 |
|---|---|---|
| 전체 | 82.2% (CI 76.0~87.1) | **96.1%** (CI 92.2~98.1) |
| 의도 파악 / 규칙 준수 | 84.8% / 75.0% | 94.7% / 100% |
| 다중 기능 | 66.7% | 100% |
| 다중 기능 순서 정확 | 24/24 | 30/30 (수정 전 22/30) |
| 지연 p50 | 2,435ms | 1,756ms |
| 실행당 LLM 호출 / 입력 토큰 | 1.59회 / 2,168 | 2.14회 / 2,229 |

  - 짝 비교 전체: S2만 정답 10, S1만 정답 1 (p=0.0117). 의도 파악·규칙 준수를 각각 보면 p=0.125(표본이 작아 유의하지 않음).
  - S1의 오답: 요청하지 않은 판매처 탐색을 붙임(15회), 필수 조건이 없는데 되묻지 않고 검색(12회) → 규칙을 프롬프트로만
    주면 지켜지지 않고, S2는 코드로 강제한다.
  - S2에서 supervisor가 "추천하고 그중 하나 분석" 요청에 분석/판매처를 먼저 실행하는 오류(30회 중 8회) 발견 → 상품 맥락이 없으면
    상품 탐색을 먼저 하도록 코드로 강제 → 30/30.
- **한계**: 다듬기 세트가 쉬워 S1을 조정할 기회가 없었다(S1이 더 좋아질 여지). 도구는 가짜라 지연은 라우팅 LLM 시간만.
  supervisor 모델(gpt-5.4-nano)이 S1(gpt-4o-mini)과 다르다.

## 처음 보는 질문으로 한 과적합 확인 (holdout)

평가셋을 보고 고친 수정(가격 범위 전달, HG·"퓨처", supervisor 순서)이 평가셋에만 맞춘 것인지 보려고, 평가셋과 겹치지 않는 질문으로
다시 쟀다. 분석 30문항은 시드만 바꾼 같은 생성 규칙(평가셋과 조건 조합 0개 겹침), 라우팅 30문항은 새로 쓰고 평가셋·프롬프트 예시와
유사도 0.45 미만을 강제했다. 실행 전에 고정했다.

- **분석(30문항 × 2회, 서비스 코드 그대로)**: 첫 측정에서 새 버그 발견 — 생성에 쓴 문서의 21.1%(62/294)가 지면 조건 불만족
  ("TF용" 지면 미인식, 위 표 8번). 수정 후 다시 잰 값: 조건 불만족 문서 **0/292**, 결과 없음 0/60, 정답 있는데 못 보여줌 0/60,
  지어낸 가격·링크 0건, 답변당 근거 없는 주장 **0.28개**(CI 0.13~0.45, 평가셋과 같음), 보여준 상품 163 → 200개.
  이 세트로 버그를 찾아 고쳤으므로 분석 쪽은 이제 완전한 holdout은 아니다.
- **라우팅(30문항 × 3회)**: 현재 버전 **90.0%**(평가셋 96.7%보다 6.7%p 낮음) vs 옛 버전 66.7%. 다중 기능 100%·규칙 준수 100%는 유지,
  분명한 질문 87.5%. 남은 오답은 요청 안 한 판매처 탐색을 붙이는 LLM 추출 오류와 "티엠포 어때?"를 되묻는 경우. 짝 비교 p=0.0923
  (30문항이라 유의하지 않음). → 평가셋 결과에는 평가셋에 맞춰진 부분이 일부 있다.
- **단일 에이전트 비교(30문항 × 3회)**: 현재 구조 92.2% vs 단일 에이전트 87.8%(p=0.5). 평가셋(96.1 vs 82.2)보다 차이가 작고 유의하지
  않다. 다중 기능 요청에서의 차이(100% vs 72.2%)와 규칙 준수(100% vs 90.5%)는 유지됐다.
  → "현재 구조가 전반적으로 낫다"보다 "다중 기능 요청과 필수 조건 규칙에서 낫다"로 범위를 좁혀 말한다.

## 자소서·포트폴리오 문장 후보

쓰는 규칙: "개선 후, 이전 방식과 같은 조건으로 다시 측정해 효과를 검증했다." 장애 주입·LLM 판정·상한값은 그대로 밝힌다.

1. **검색 필터** — 검색 필터를 매번 LLM으로 만들던 구조를, 이미 추출된 조건을 메타데이터 필터에 바로 넣는 구조로 바꿨습니다.
   같은 질문 30개 × 3회로 다시 측정한 결과 검색 지연 p50은 1,364ms에서 233ms로 줄었고, LLM이 없는 조건을 지어내 결과가
   0개가 되던 경우(90회 중 17회)가 사라졌습니다.
2. **"효과 없음"을 실험으로 찾은 경험** — hallucination 방지용으로 넣은 LLM 채점 단계(CRAG·Self-RAG)를 ablation으로 검증하니
   근거 없는 주장 수는 줄지 않았고(p=1.0) 지연만 27% 늘었습니다. 원인을 추적해 생성 프롬프트 한 줄이 문서에 없는 기능 설명을
   요구하고 있음을 찾았고, 그 줄을 고치고 LLM 채점을 결정적 검사로 바꿔 답변당 근거 없는 주장을 2.56개에서 0.23개로,
   LLM 호출을 3회에서 1회로 줄였습니다. 프롬프트는 YAML로 분리해 버전과 근거를 남깁니다.
3. **캐시와 장애 대응** — 크롤링 캐시를 사용자 응답 시간 기준으로 재측정해(판매처 4곳 24쌍) p50이 73초에서 4.9초로 줄고 캐시
   응답이 실제 크롤링과 같은 문서를 쓰는 것을 확인했습니다. 측정 중 판매처 장애 때 요청마다 23초를 기다리는 문제를 발견해
   실패 캐시를 넣었고, 실측 타임아웃을 주입한 측정에서 장애 중 응답이 28.6초에서 5.5초로 줄었습니다.
4. **라우팅** — 한 턴에 의도 하나만 고르던 라우팅을 다중 기능 + 조건 게이트로 바꾸고 같은 60문항 × 3회로 검증해 정답률을
   66.7%에서 96.7%로(p=0.0001), 다중 기능 요청을 0%에서 100%로 올렸습니다. 평가 중 규칙 코드의 조건 누락 2건을 찾아 고쳤습니다.
5. **구조 선택의 근거** — 같은 프롬프트·규칙을 가진 단일 ReAct 에이전트와 비교했습니다. 평가셋에서는 96.1% 대 82.2%(p=0.0117)였지만
   처음 보는 질문에서는 92.2% 대 87.8%로 차이가 줄었고, 일관되게 남은 차이는 다중 기능 요청(100% 대 72%)과 필수 조건 규칙이었습니다.
   그래서 "규칙과 실행 순서는 프롬프트가 아니라 코드로 강제해야 한다"는 범위로 결론을 냈습니다.
6. **holdout이 버그를 찾음** — 평가셋을 보고 고친 수정이 과적합인지 확인하려고 처음 보는 질문으로 다시 쟀더니, "TF용"처럼 한글이 붙은
   지면을 못 잡는 버그가 드러났습니다(생성 문서의 21% 조건 불만족 → 수정 후 0%). 라우팅 정답률은 평가셋보다 6.7%p 낮게 나와
   평가셋에 맞춰진 부분이 있음을 그대로 보고했습니다.

## 면접 예상 질문

- **LLM 판정을 어떻게 믿나?** → 생성 모델과 다른 모델(gpt-4o)이 판정하고 어느 방식의 답변인지 모르게 했다. 사람 검수 30건 중
  초기 20건은 일치, 최종 10건에서 판정자 오판 3건을 찾아 최종 수치는 상한으로 보고한다. 가격·링크는 LLM 없이 코드로 대조했다.
- **질문을 직접 만들면 유리하게 만든 것 아닌가?** → 실험 1은 실제 DB 조합에서 시드 고정 규칙으로 생성, 실험 4·5는 프롬프트 예시와
  유사도 0.45 미만을 assert로 강제, 애매한 질문 정답은 실행 전 승인 후 고정했다. 그래도 사람 검수가 없다는 한계는 남는다.
- **정답 기준이 새 정책이면 옛 버전에 불리하지 않나?** → 맞다. 그래서 정책과 무관한 "의도 파악" 항목(75.0% → 95.5%, p=0.0225)을
  따로 보고한다.
- **평가셋에 과적합된 수정 아닌가?** → 처음 보는 질문 세트로 다시 쟀다. 분석은 같은 수준(근거 없는 주장 0.28개)이 나왔고 새 버그를
  하나 더 찾았다. 라우팅은 96.7% → 90.0%로 평가셋보다 낮아 일부 과적합이 있었다고 본다.
- **표본이 작지 않나?** → 비율에는 신뢰구간, 비교에는 질문 단위 짝 검정을 붙였고, 유의하지 않은 항목(실험 5의 세부 항목 p=0.125,
  실험 2의 p=1.0)도 그대로 적었다.
