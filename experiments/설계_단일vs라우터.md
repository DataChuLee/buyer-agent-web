# 실험 설계: 단일 에이전트 vs 라우터 + 하위 에이전트 (1단계 초안)

- 기준 코드: `main` `a8ca6f4` (2026-10-28)
- 질문 초안: `questions_draft.csv` (다듬기용 6개 + 평가용 30개). 정답은 아직 확정 전.

## 비교 조건

| 조건 | 구성 |
|---|---|
| S1 단일 에이전트 | ReAct 에이전트 1개(gpt-4o-mini, temp 0). 도구: `search_products`, `search_sellers`, `analyze_product`(분석 함수를 도구로 감쌈), `ask_user`. 프롬프트는 의도 분류 프롬프트, supervisor 프롬프트, 필수 조건 규칙, 하위 에이전트 프롬프트를 하나로 합침 |
| S2 현재 구조 | 실제 `extract_conditions_and_intent` → `check_conditions` → `supervisor_node` 코드를 그대로 사용 |

- 두 조건 모두 도구는 가짜(stub)이고 같은 응답 파일을 씁니다. LLM 시간만 잽니다.
- 측정 대상은 "이번 턴에 어떤 도구 묶음을 부르는가"입니다.
  - S2는 워커가 사용자 선택 대기(`interrupt`)에서 멈추므로, 실제로 실행된 워커가 아니라 **조건 점검을 통과한 `requested_capabilities`와 되묻기 여부**로 채점합니다.
  - S1은 한 턴 동안 호출한 도구 집합으로 채점합니다.
- 채점 단위(도구 묶음): `product_search`, `seller_search`, `product_analysis`, `ask`(되묻기), `none`(도구 없음)
- 지표
  - 정답률(묶음 집합 완전 일치)
  - 오호출 비율(정답에 없는 묶음을 부름)
  - 미호출 비율(정답 묶음을 빠뜨림)
  - 순서 일치율(기능이 여러 개인 질문만)
  - S2 의도 정확도
  - 질문당 토큰, p50 지연(라우팅 단계 비용 포함, LangSmith 트레이스로 수집)

## 가이드에서 바꾼 점과 이유

1. **S1+R을 만들지 않습니다.** supervisor는 도구를 직접 호출하지 않는 라우터(구조화 출력)이고 하위 에이전트마다 도구가 1개라서, 가이드의 S1+R 조건(오케스트레이터가 도구를 호출하는 LLM 에이전트)에 해당하지 않습니다.
2. **기능이 여러 개인 질문 6개를 평가 세트 안에 넣었습니다.** 가이드에서는 별도 보고로 뺐습니다. 하지만 지금 구조의 핵심 차별점이 다중 기능 요청이라, 빼면 비교의 핵심을 놓칩니다. 구성은 분명한 질문 7, 다중 기능 6, 헷갈리는 질문 11, 도구 없음 6입니다.
3. **S1 도구에 `ask_user`를 추가합니다.** S2에서는 되묻기가 명시적인 경로이므로, S1도 되묻기를 도구 선택으로 측정해야 같은 조건이 됩니다.
4. **S1 프롬프트에 서비스의 필수 조건 규칙을 그대로 넣습니다.** 제품 탐색에는 브랜드·예산·지면이, 판매처 탐색과 분석에는 상품명이 필요하다는 규칙입니다. 이것은 구조 문제가 아니라 제품 정책이라, S1에서 빠지면 S1을 일부러 약하게 만든 셈이 됩니다.
   - 차이가 나는 지점은 "S2는 규칙 코드로 판정하고, S1은 LLM이 판정한다"입니다.
5. **구매 의도(`purchase_prepare`)는 제외합니다.** 직전 분석 결과가 있어야 해서 한 턴 범위를 벗어납니다.
6. **기존 질문과 겹치는 문장을 쓰지 않았습니다.** 기존 의도 분류 질문 세트 20개와 의도 분류 프롬프트 안의 예시 8개는 S2를 다듬을 때 쓰였을 수 있어서, 같은 문장이 없는지 assert로 확인했습니다.
